# store

The Quarterdeck store: one in-process [PGlite](https://pglite.dev) Postgres per project, or one external Postgres for every project when `DATABASE_URL` is set. Both run the same queries and the same migrations from plain SQL files on every start.

## Choosing the backend

| Given                                        | Backend                                              |
| -------------------------------------------- | ---------------------------------------------------- |
| `dataDir`                                    | PGlite at that dir, even when `DATABASE_URL` is set. |
| `databaseUrl`, or a non-empty `DATABASE_URL` | External Postgres at that URL.                       |
| Neither                                      | PGlite at `~/.quarterdeck/<project>/pg`.             |

External Postgres must be 15 or newer (`0001_init` uses `unique nulls not distinct`). `openStore` checks `server_version_num` before migrating and throws `Quarterdeck needs Postgres 15 or newer; this server is Postgres 14.x` on anything older. A failed connection throws `Could not connect to Postgres at <url>` with the password removed.

## Where the data lives

`~/.quarterdeck/<project>/pg` is the PGlite data dir for one project. Deleting that folder deletes the project's state; the next `openStore` recreates it empty.

`~/.quarterdeck` is private to the user. `openStore` creates it, the project dir and the data dir as `0700` and tightens any of them it finds looser; `quarterdeck init` does the same for the home. Every directory Quarterdeck creates under it (builder worktrees aside) is `0700` (`ensurePrivateDir`) and every file it writes there is `0600` (`writePrivateFile`, which also tightens a file it overwrites). Windows has no such modes; there the calls create and write without checking them.

`~/.quarterdeck/<project>/turns/<agent-id>/<seq>/` holds one agent turn as plain files: `input.md` (the prompt), `output.md` (the agent's reply text), `updates.jsonl` (every ACP session update of the turn) and, once it parsed, `result.json` (`projectTurnsDir`; see [driver](../driver/README.md#turn-files)). The `turns` row's `transcript_path` names the folder. These files are written on both backends, and wiping the project deletes them.

`~/.quarterdeck/<project>/worktrees/<builder>-<ticket>/` is the git worktree a builder works a ticket in (`projectWorktreesDir`; see [driver](../driver/README.md#builders)), `<ticket>` being the first 8 characters of the ticket id. Each is registered with the project's repository. Retiring the builder removes it; wiping the project deletes the folder, unsaved work included, and `git worktree prune` in the repository then drops the stale registration.

`~/.quarterdeck/pause.json` exists only while everything is paused (`pause.all`; see [pause](../pause/README.md)) and holds `{ "pausedAt": "<iso>" }`. Deleting it lifts the global pause. It is the same on both backends, and wiping projects leaves it alone.

`~/.quarterdeck/workspace.json` is the workspace: `{ "root", "mode": "single" | "multi", "projects": [{ "slug", "name", "repoPath", "repository" }], "updatedAt" }`, written by `quarterdeck init`, by `project.create` through the API, and once at startup from the open projects when it does not exist (see [workspace](../workspace/README.md)). It is not in any database, so it is the same on both backends; wiping a project drops it from `projects` and leaves the rest. Deleting it makes the next start seed it again: one project with a repository is `single`, more are `multi`.

`~/.quarterdeck/layout.json` is the dashboard's layout, one for every project: `{ "spec": <layout>, "updatedAt": "<iso>" }`, written by `layout.save` and `layout.reset` without a project (see [api](../api/README.md#dashboard-layout)). It is not in any database, so it is the same on both backends, and wiping projects leaves it alone. Deleting it puts the dashboard back on its default preset; the next start seeds it again from the newest per-project `dashboard` row, if any is left.

`~/.quarterdeck/sock/<hash>.sock` (or `$TMPDIR/quarterdeck-<uid>/<hash>.sock` when the home path is too long) is a project's bus MCP socket; see [bus](../bus/README.md#socket-path). It holds no data, exists only while the server is up, and is removed on shutdown. This is the same on both backends.

`~/.quarterdeck/plugins/<name>.mjs` is a ticket-source plugin you put there yourself; see [tickets](../tickets/README.md#plugins). Plugins are superseded by [project services](../services/README.md). It holds code, not data, and Quarterdeck only reads it. This is the same on both backends.

With `DATABASE_URL`, every project shares that database: one set of tables, rows scoped by `project_id`. Nothing is written under `~/.quarterdeck/` for the store; turn files still are, and a wipe removes `~/.quarterdeck/<project>/` after the rows. The project list comes from the `projects` table (`listProjectSlugs`, `projectRowExists`), read through one `createPostgresPool` that the API keeps for its lifetime. Wiping a project (`wipePostgresProject`) takes its advisory lock, so it fails with `ProjectOpenError` while another process has the project open. It then deletes the project's rows from every `STORE_TABLES` table that has a `project_id` (`deleteProjectRows`), and finally the `projects` row, which also cascades `turns`, all in one transaction.

## One opener per project

PGlite: `~/.quarterdeck/<project>/pg.lock` holds the pid of the process that has the project open. PGlite takes no lock of its own, and two processes on one data dir silently lose each other's writes, so `openStore` creates this file exclusively and throws `project <p> is already open (pid N)` while that pid is alive. A lock left by a dead pid is reclaimed. `close()` removes it, as does a failed open. `IN_MEMORY` stores are not locked.

External Postgres: there is no data dir and no lock file. `openStore` takes a session advisory lock for the project (`pg_try_advisory_lock(hashtext('quarterdeck_project'), hashtext(<project>))`) on a dedicated connection that it keeps for the life of the store, and throws `project <p> is already open by another connection to this database` when another opener holds it. Different projects open side by side. `close()` releases the lock, and so does the connection dropping, so a crashed process never leaves a project stuck. Migrations take `pg_advisory_xact_lock(hashtext('quarterdeck_migrations'))` and recheck `schema_migrations` inside each migration's transaction, so openers that start together apply each migration exactly once.

The session connection fails closed. If it ends or errors for any reason other than `close()` (server restart, failover, idle timeout, `pg_terminate_backend`), the project lock and every `LISTEN` are gone. The store does not reconnect. Every later `query`, `exec`, `transaction`, `listen`, `publish` and `subscribe` rejects with `StoreConnectionLostError`, and so does a transaction that reaches `commit` after the loss. Every open subscription and watcher gets that error once through `onError` and is closed. Treat `StoreConnectionLostError` as "restart": `close()` the store and `openStore` again, which takes the lock again or fails if another process now holds the project.

## API

```ts
import { openStore } from '@quarterdeck/server';

const store = await openStore({ project: 'example' });
await store.db.query('select * from tickets where project_id = $1', [
  store.projectId,
]);
const subscription = await store.subscribe((event) => broadcast(event));
await store.publish({ kind: 'ticket.created', payload: { title } });
await subscription.close();
await store.close();
```

## Event bus

Every insert into `events`, through `publish` or plain SQL, fires `pg_notify` on `EVENTS_CHANNEL`. A subscription treats the notification only as a wake-up: it then reads `events` where `id` is past its `cursor`, in batches of `EVENT_BATCH`, so it never depends on the notification payload, never sees another project's events, and never gets an event twice.

Reading past a cursor only works if ids become visible in id order. The `events_order` trigger (`0005_event_order`) guarantees that on every backend. Before each insert it takes `pg_advisory_xact_lock(hashtext('quarterdeck_events'), hashtext(project_id))` and only then assigns `id` from `events_id_seq`. The column has no identity or default, so each event draws exactly one id. Transactions that insert events for the same project queue on that lock until the holder commits, so a later id never commits before an earlier one. The lock is held until commit, so keep event-inserting transactions short and record the event last: a transaction that holds the event lock and then waits on a row lock held by another event-inserting transaction deadlocks, and Postgres aborts one of them. On PGlite, transactions already run one at a time, so the lock costs nothing.

- With no `after`, a subscription starts at the newest event and delivers only what is inserted from then on.
- `subscription.cursor` is the id of the last event handed to `handler`. Pass it back as `after` to resume after a disconnect, a closed subscription or a restart; everything inserted in between is replayed first, then live events follow. `after: 0` replays the whole log.
- A handler that throws, or a failed read, goes to `onError` (default: `console.error`) and the subscription keeps going. The failed event is not retried.
- `subscription.close()` stops delivery and waits for the handler call in flight. Calling it twice is safe.

`StoreEvent` is `{ id, projectId, agentId, ticketId, kind, payload, createdAt }`.

## Table changes

Every insert, update and delete on a table in `WATCHED_TABLES` (every table but the `events` and `intents` logs; each recorded intent already writes an event) fires `pg_notify` on `CHANGES_CHANNEL` (`quarterdeck_changes`) with `{"table","op","id","project_id"}`. A watcher drops other projects' notices (but keeps a `notebook` row with no project, an entry for every project, which `readRows` and `readRow` also read), re-reads the row by `id` and calls `handler` with a `TableChange`: `{ table, op, id, row }`, where `row` has camelCase keys and is `null` for a delete (or a row deleted before it was read). Because the row is read at delivery, it is always the latest state, never an older version.

Changes have no cursor: a notification sent while nobody is watching is gone. Read the tables again after reconnecting (`readRows(db, projectId, table, { turnsPerAgent? })`), which is what the stream's snapshot does; `turnsPerAgent` keeps only each agent's latest turns.

`turns` rows, from `watch` and `readRows`, leave out `prompt`: it can be large and lives in the table, so read it on demand. A turn's project comes from its agent. When an agent is deleted its turns go with it by cascade and have no project left to report, so those turn deletes reach no watcher. Drop an agent's turns when its delete arrives.

## Migrations

`migrations/NNNN_name.sql`, applied in version order, each in its own transaction together with its row in `schema_migrations`. A failing migration rolls back and stays pending. Any other `*.sql` name in the folder (`0002_AddX.sql`, `2_x.sql`) makes `migrate` throw before anything runs. Tables with `updated_at` keep it current through the `touch_updated_at` trigger. Never edit a migration that has merged; add the next number. `npm run build` copies `migrations/` to `dist/store/migrations/` so the built package finds them next to `dist/store/migrate.js`.

`0024_voyages` renamed what migrations before it called rounds to voyages: the table (with its constraints and `voyages_change` trigger) and every `voyage_id` column. It also rewrites the rows written under the old names, so readers only ever see the new ones: event and intent kinds become `voyage.*` and `driver.voyage_started`, the `roundId` and `round` keys of event payloads and intent inputs and results become `voyageId` and `voyage`, and a `crew.failed` event's `service` becomes `voyages`. Free text already stored (error messages, notebook bodies) is left as written. Turn files on disk are not rewritten either; the [Driver](../driver/README.md#finding-a-voyages-driver) still reads a birth input saved before the rename. Migrations `0001` to `0024`, the test that seeds a store with them and that birth-input pattern are the only places the old names remain.

`0026_global_voyage` is for the voyage that spans every project (see [crew](../crew/README.md#voyages)): each project's `voyages` row lists the voyage's projects in `projects` (empty on older rows), a `notebook` entry with no `project_id` is one for every project, and a `notebook_proposals` row with `global` set adds one.

## Tables

| Table                | Holds                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `projects`           | One row per project: `slug`, `name`, `repo_path`, `archived_at` (set once archived; its agents are retired and no longer hold their names), and the [services](../services/README.md) `tracker` (jsonb) and `publishes`, `null` until set (migration `0025_project_services`).                                                                                                                                                                 |
| `voyages`            | This project's row of each voyage: `number` (counted across every project since `0026_global_voyage`), `status` planning / active / ended, `goal`, `projects` (every project in the voyage).                                                                                                                                                                                                                                                   |
| `agents`             | Planner, Driver, builders, reviewer (the Driver and reviewer as one seat per project, sharing a name): `name` (unique among agents not `retired`), `role`, `runtime`, `status`, and `pid` / `pid_started_at` while its process group may be running (migration `0022_agent_pids`).                                                                                                                                                             |
| `tickets`            | Local tickets: `status`, `assignee_id`, `depends_on` (ticket ids in any project, so not foreign keys; see [dependencies](../driver/README.md#dependencies)), `source` + `external_id` for the superseded ticket-source plugins, `external_ref` (the tracker's id for it, set by the Planner and shown to agents), `pr_url`, `head_sha`. The Planner's proposals are `proposed` until the human approves (`open`) or rejects (`rejected`) them. |
| `cards`              | Human gates: `kind`, `question`, `options`, `checked`, `recommendation`, `status` open / answered / declined / expired, `answer`, `expires_at`, and `sign_in` (jsonb), the live state of a sign-in card's automated sign-in (migration `0027_card_sign_in`; see [signin](../signin/README.md#the-card)).                                                                                                                                       |
| `turns`              | One ACP prompt turn per row: `agent_id`, `seq`, `prompt`, `stop_reason`, token counts, `transcript_path`.                                                                                                                                                                                                                                                                                                                                      |
| `events`             | Append-only event log with `kind` and `payload`; inserts notify `EVENTS_CHANNEL`.                                                                                                                                                                                                                                                                                                                                                              |
| `notebook`           | Entries the next Driver is born with: `body`, `pinned`, `author_id`, `voyage_id`, `retired_at` (set once retired; a retired entry is no longer active). No `project_id` makes it an entry for every project.                                                                                                                                                                                                                                   |
| `notebook_proposals` | Notebook changes a Driver proposed at wrap-up: `op` add / update / retire, `entry_id` (update and retire), `body` (add and update), `pinned`, `global` (an add for every project), `rationale`, `voyage_id`, `agent_id`, `status` open / accepted / rejected.                                                                                                                                                                                  |
| `charter_proposals`  | Proposed charter changes: `body`, `rationale`, `voyage_id`, `status` open / accepted / rejected.                                                                                                                                                                                                                                                                                                                                               |
| `budget`             | Token and USD limits and spend, one row per (project, voyage, agent) scope; null voyage/agent is wider.                                                                                                                                                                                                                                                                                                                                        |
| `layouts`            | This project's named layouts as JSON `spec`, unique by `name`. The dashboard's own grid is no longer here but in `~/.quarterdeck/layout.json`; a `dashboard` row left from before is kept, and read only at startup to seed that file while it does not exist. Shipped presets live in `src/layouts/presets.ts`, not here.                                                                                                                     |
| `intents`            | Every intent the HTTP API accepted: `kind`, `input`, `status` pending / applied / rejected, `result`, `settled_at`, and `seq`, the insertion order that breaks a `created_at` tie (migration `0023_intent_order`).                                                                                                                                                                                                                             |
