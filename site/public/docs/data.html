Where your data lives

Everything Quarterdeck stores is on your machine, in one folder: ~/.quarterdeck/. There is no hosted component and no telemetry, and you can open, read and delete all of it.

The dashboard's Data widget shows the same thing for the open project: every table with its row count, the rows themselves a page at a time, and every path below with whether it exists yet.

The folder

~/.quarterdeck/
  rules.local.<file>           your machine's rules
  claude.json                    which Claude auth mode this machine uses
  profiles/<name>/               rules profiles you add yourself
  <project>/
    pg/                          the project's Postgres data
    pg.lock                      which process has the project open
    turns/<agent-id>/<seq>/      one folder per agent turn
    worktrees/<builder>-<ticket>/  a builder's git worktree
    attachments/<id>.<ext>       images attached in the dashboard chat
  plugins/<name>.mjs             ticket-source plugins you add yourself
  workspace.json                 your workspace: root folder, single or multi, projects
  pause.json                     only while everything is paused
  sock/<hash>.sock               a project's bus socket, while running
  _deck/                         where the Driver and the reviewer run
  kiro/                          where kiro-cli runs
  gemini/                        where gemini runs, and its locked settings
  runtimes/claude/               where the Claude Code agent runs
Path What it holds
~/.quarterdeck/rules.local.<file> Your machine's rules overrides. Configuration, not state: wiping projects leaves them.
~/.quarterdeck/claude.json The Claude auth mode (subscription, api_key or vertex), when you set it in a file rather than in QUARTERDECK_CLAUDE_AUTH. It holds the mode only, never a key. Wiping leaves it.
~/.quarterdeck/profiles/<name>/ Rules profiles you add with profile add: a profile.json naming the standards docs it reads, and any reviewer, charter or lifecycle layer. rules.local.profile.json picks the active one. Configuration, not state: wiping projects leaves them.
~/.quarterdeck/<project>/pg/ The project's store: a real Postgres data directory (PGlite), one per project. Tickets, agents, events, cards, turns, saved dashboard layouts and the rest. Deleting it deletes the project's state.
~/.quarterdeck/<project>/pg.lock The process id of the Quarterdeck that has the project open, so two never write the same data directory. Removed on close.
~/.quarterdeck/<project>/turns/<agent-id>/<seq>/ One agent turn as plain files: input.md (the prompt), output.md (the reply), updates.jsonl (every update the agent sent) and, when the turn ends in a result Quarterdeck can read, result.json. <seq> counts each agent's turns from 0001.
~/.quarterdeck/<project>/worktrees/<builder>-<ticket>/ The git worktree a builder works a ticket in, registered with your repository. <ticket> is the first 8 characters of the ticket id. Retiring the builder removes it.
~/.quarterdeck/<project>/attachments/<id>.<ext> Images you attached to a Planner message or a card answer in the dashboard: PNG, JPEG, GIF or WebP, up to 5 MB each. The conversation and the card keep only each image's id, type, size and path, so the transcript still shows it after a reload. Wiping the project deletes them.
~/.quarterdeck/plugins/<name>.mjs Ticket-source plugins you put there yourself. Code, not data: Quarterdeck only reads them, and wiping leaves them. Superseded: a project now names its tracker in services.json or the Project widget, and agents reach it themselves.
~/.quarterdeck/workspace.json The workspace init picked: its root folder, whether it is one repository (single) or a folder of projects (multi), and its projects. The Data widget shows it on its own line. Wiping a project drops it from the list; deleting the file makes the next start write it again from the projects there are.
~/.quarterdeck/pause.json Exists only while everything is paused, and holds when the pause began. Deleting it lifts the pause. Wiping leaves it.
~/.quarterdeck/sock/<hash>.sock The socket a project's agents reach Quarterdeck's tools on. It holds no data and is removed on shutdown. When the path would be too long it goes in $TMPDIR/quarterdeck-<uid>/ instead.
~/.quarterdeck/_deck/ The folder the Driver and the reviewer run in. They work every project, so they start in none of your repositories. It holds no data, and wiping leaves it.
~/.quarterdeck/kiro/, ~/.quarterdeck/gemini/, ~/.quarterdeck/runtimes/claude/ The folders each runtime's process runs in, so nothing in your repository can change how it starts. gemini/ also holds the settings and policy that keep Gemini asking before it uses a tool.

Outside the folder

  • <repo>/.quarterdeck/rules.local.<file>: a project's own rules. Quarterdeck writes here only after you agree to it in quarterdeck init, when you save a rule for one project, or when you accept a charter proposal.
  • ~/.kiro/agents/quarterdeck-<project>-<agent>.json: the agent config Kiro needs to start an agent. It is removed when the agent's process exits.
  • Your runtimes' and gh's own sign-ins stay where those tools keep them. Quarterdeck does not copy or store them.
  • An Anthropic API key for the api_key mode stays in your environment (ANTHROPIC_API_KEY) or the macOS Keychain (quarterdeck-anthropic-api-key). Quarterdeck hands it to the Claude agents it starts and nothing else: it is never written to a project's database, an event, a turn file or the notebook, and anything shaped like sk-ant- is stored as [redacted]. Vertex credentials stay with gcloud.

Your own Postgres

Set DATABASE_URL before quarterdeck up and every project is stored in that database instead, one set of tables with rows kept apart by project. Nothing is written to ~/.quarterdeck/<project>/pg/; turn files, worktrees and attachments still are.

Importing from Harness

If you used Harness before, one command moves its projects, its open docket items and its active notebook entries into Quarterdeck. Stop Quarterdeck and end any voyage first: the import refuses to run while a voyage is open. It reads Harness in one read-only transaction and never writes to it. Give it the connection string in HARNESS_DATABASE_URL; it is never printed, logged or saved. 

HARNESS_DATABASE_URL=postgres://… npm run quarterdeck -- import harness
HARNESS_DATABASE_URL=postgres://… npm run quarterdeck -- import harness --apply

The first command is a dry run: it prints, per project, what it would create or update and every mapping decision, and writes nothing. With --apply it writes. Each Harness project becomes a project (or matches one you already have by name), each docket item a ticket in it, with its dependencies pointing at the new tickets, and each notebook entry an active one, pinned as before; a global Harness entry becomes one global notebook entry, for every project. Items that were in flight in Harness come in as open with their pull request and a note saying so; no agent is carried over. Harness's Copilot review and auto-merge settings go into ~/.quarterdeck/rules.local.lifecycle.json. Reviewers are printed for you to set up, not imported. Archived projects are skipped unless you pass --include-archived.

Running it again updates what it brought in before and adds nothing twice. Tickets Quarterdeck has already started on are left as they are. Imported tickets keep the Harness id in external_id, with source harness, and imported notebook entries keep it in their own external_id.

Deleting it

Stop Quarterdeck first. Then delete ~/.quarterdeck/<project>/ to remove one project (its state, its turn files, its attachments and its worktrees, unsaved work included), or ~/.quarterdeck/ to remove everything. After deleting worktrees, run git worktree prune in your repository to drop their registrations. 

rm -rf ~/.quarterdeck/my-app
git -C path/to/your/repo worktree prune

Or use the Wipe buttons in the Data widget while Quarterdeck runs. Wipe project asks you to type the project's name; Wipe everything asks you to type wipe everything. Either stops the project first: it is archived so nothing new starts, every live agent is killed, every process group Quarterdeck started for it is swept, and each worktree is removed from your repository. Then the project's folder is deleted and, with DATABASE_URL, its rows in your database. If a process cannot be confirmed stopped, the wipe is refused and the project kept, so the next start can sweep it. Wiping keeps your machine rules (~/.quarterdeck/rules.local.*); delete those yourself if you want them gone.

With Quarterdeck stopped, the same wipe runs from a terminal and asks for the same name. In a script, pass that name as --confirm. 

npm run quarterdeck -- wipe my-app
npm run quarterdeck -- wipe --all --confirm "wipe everything"
