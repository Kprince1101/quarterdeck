Voyages

A voyage is one run of work toward a goal, from Start voyage until it ends. One voyage runs at a time, and it spans every project you have added: one Driver coordinates it and one reviewer reviews it, whichever repository the work is in.

A voyage is not an ACP session. A session is one agent's conversation with its runtime; a voyage holds many of them, the Driver's, the reviewer's and one per builder.

The Planner and spec tickets

The Planner is one conversation for every active project. You describe what you want; it proposes tickets, and each one names the project it belongs to. You approve, edit or reject each proposal in the Planner widget, and editing one can move it to another project. Only approved tickets reach the Driver.

Every ticket is a spec, in the shape Kiro uses, so a builder starts with requirements, a design and a task list: 

## Requirements

- As a maintainer, I want …
  - WHEN … THE SYSTEM SHALL …

## Design

Where in the repository, the approach, the constraints and decisions.

## Tasks

1. A numbered checklist sized for one pull request.

Proven: <observable check>

A proposal that names no active project or does not follow this format never reaches the board: the Planner is told what is wrong and asked once more. The spec lives in the ticket only; nothing is written to the repository. A ticket can also carry its id in the project's tracker, its external_ref (see project services).

One Driver, one reviewer

Start voyage births the Driver, the coordinator for every project with a repository. It is told whenever something it should act on happens in any of them: a ticket approved, a builder's turn ended, a pull request reported, a verdict, a merge. Each line names its project. It births builders, assigns them tickets, keeps them going, and asks you a card when a decision is irreversible or product-shaped.

Each builder works one ticket in its own git worktree of that ticket's project and opens a pull request there. There is one reviewer for every project, kept between voyages; it reads each request against reviewer.md and approves it or sends it back. Then the project's merge gate decides whether it merges.

A voyage ends itself once nothing is open and it has stayed settled for autoEndSettleSeconds. The Driver then gets a wrap-up turn and proposes notebook entries and charter edits for you to approve.

Work across projects

A ticket can depend on tickets in any project. An approved ticket waits until everything it depends on is done, and the Events feed says what it is waiting for. The Driver can also block a ticket a builder already holds on tickets elsewhere; the builder keeps its worktree and session while it waits.

A project marked publishes is a library: merging one of its tickets is not enough for the projects that depend on it, because they need a release. When such a ticket merges, the Driver is asked to publish it with the project's own tooling and then send the published action with the package and version. Quarterdeck never publishes anything itself. Until then, dependents read merged but not published yet.

Once every dependency of a ticket is satisfied, Quarterdeck acts without waiting to be asked. A blocked builder is woken by itself, told which package versions to bump, and carries on. An unassigned ticket that is now ready goes to the Driver, which assigns it.

Steering one project

The Board lists each project in the voyage with its own Kill, which stops that project's builders and blocks their tickets while the voyage, the Driver and every other project keep going. Pausing a project holds its launches and continues and nothing else. Kill all ends the voyage everywhere and reopens its tickets.

GitHub and GitLab

Each project is on the forge its origin remote points at: github.com is GitHub, gitlab.com is GitLab, and a self-hosted instance is mapped once in forges.json. On GitHub, agents and the dashboard say pull request (PR) and use gh; on GitLab they say merge request (MR) and use glab, and npm run quarterdeck -- doctor checks glab for each GitLab host. One voyage can mix both.

The merge gate can also wait for an AI review: requireAiReview holds a request until one of the forge's aiReviewers has reviewed it and every thread it opened is resolved. On GitHub those ship as the Copilot reviewer's logins. GitLab ships none, so you name your bot in your machine layer; until you do, the gate stops with an error rather than pass. The old requireCopilotReview key is deprecated and reads as requireAiReview.

Project services

Each project tells its agents how to reach the outside world: its forge, detected from the remote, and its ticket service (a tracker such as Jira or Targetprocess), reached through a CLI command or an MCP server you name in the Project widget or in services.json. Every prompt for work on a ticket carries a Services section with them, and a builder's and the reviewer's add the ticket's external_ref, so an agent can update the tracker item itself. Quarterdeck never calls the tracker. This supersedes the ticket-source plugins in ~/.quarterdeck/plugins/.

Kiro base agents

On Kiro, the Driver, the reviewer and the builders can each start from one of your own Kiro agents, with its MCP servers, steering, skills, prompt and model. A project can give its builders a different base from its own repo layer, so a component library's builders and an app's need not match. Hooks are never copied from a base. See kiro.json.

How Quarterdeck fits a multi-repo effort

Take two libraries and three apps: ui-kit, a React component library; ui-extras, a library of bespoke components built on ui-kit; and retrofit-a, retrofit-b and retrofit-c, three existing apps moving onto them. A new component has to land in ui-kit, be wrapped in ui-extras, be published, and then be adopted by all three apps.

  1. Add the five repositories. Run npm run quarterdeck -- init <path> for each, then one npm run quarterdeck -- up. If retrofit-c lives on a self-hosted GitLab, map its host in forges.json; its agents then work with merge requests and glab.
  2. Mark the libraries. In the Project widget, turn on publishes for ui-kit and ui-extras, and name each project's tracker if it has one. Optionally give ui-kit's builders their own Kiro base agent from its repo layer.
  3. Plan once. Tell the Planner what you want. It proposes a spec ticket per project: the component in ui-kit; the wrapper in ui-extras, depending on the ui-kit ticket; and an adoption ticket in each retrofit app, depending on the ui-extras ticket. Approve them.
  4. Start one voyage. One Driver coordinates all five projects and one reviewer reviews every pull or merge request. The Driver assigns the ui-kit ticket; the rest wait on their dependencies, or the Driver starts retrofit prep work and blocks it on the library ticket.
  5. Merge, then publish. When the ui-kit request merges, its dependents still wait: it is merged but not published yet. The Driver publishes ui-kit with the repository's own release tooling and sends published with the package and version. The ui-extras ticket is now ready; its merge and publish follow the same way.
  6. The retrofit work wakes up. Once ui-extras is published, the ready retrofit tickets go to the Driver, and any retrofit builder it had blocked is woken by itself with the versions to bump. Three builders work three worktrees in parallel; the reviewer reads each request, and each project's merge gate merges it under that project's rules.
  7. Steer per project. If retrofit-b goes wrong, pause it or Kill its builders from the Board; everything else carries on. The voyage ends itself once everything has merged and settled.
