Rules

Rules are files. Quarterdeck ships the defaults in rules/; you change them with rules.local.* files next to them, on your machine or in one repository.

The files

File What it sets
charter.md The Driver's charter: who is on the crew, how work is assigned, when to stop for you.
reviewer.md The reviewer's prompt: what to read and when to approve.
permissions.json What an agent may do without asking you.
naming.json The naming theme and the list of agent names.
lifecycle.json Auto-end settle time, stuck threshold, budget, merge gate.
models.json The runtime (kiro, claude or gemini) and optional model for each role.
env.json Extra environment variables agents get from the server's environment.
kiro.json The Kiro agent each role starts from.
forges.json Which forge (GitHub or GitLab) any other git host is.
services.json Each project's tracker and how agents reach it, and whether it publishes.
profile.json The active rules profile and local rule levels: the standards doc and steering block builders and the reviewer read at kickoff.

Layers

To change a rule, create a file named rules.local. followed by the file's name, for example rules.local.lifecycle.json. Quarterdeck reads three layers, and the last one wins:

  1. rules/<file>, shipped with Quarterdeck.
  2. ~/.quarterdeck/rules.local.<file>, for every project on this machine.
  3. <repo>/.quarterdeck/rules.local.<file>, for one project.

JSON layers merge key by key, so an override only needs the keys it changes. Arrays are replaced whole. A Markdown layer replaces the file below it. Every layer is checked against the rule's schema, and an error names the file that broke it. For example, ~/.quarterdeck/rules.local.lifecycle.json with only this in it changes the stuck threshold and keeps every other default: 

{ "stuckAfterMinutes": 45 }

quarterdeck init writes rules.local.models.json when you pick a runtime other than the default, in whichever of the two folders you choose. Accepting a charter proposal writes <repo>/.quarterdeck/rules.local.charter.md.

The repo layer can only tighten

A .quarterdeck/ folder inside a repository can be committed, and anyone with push access can change it. So for the rules that guard you, the repo layer can make Quarterdeck stricter but never looser. Your machine layer sets them freely.

Permissions

<repo>/.quarterdeck/rules.local.permissions.json is not merged into the machine rules. It is decided on its own, it may only say deny or ask, and the stricter of its answer and the machine's answer wins. An allow in it is an error naming the file. This one keeps agents in the project away from .env files, whatever the machine allows: 

{
  "rules": [{ "kind": "read", "pattern": "**/.env*", "decision": "deny" }]
}

Merge gate

In <repo>/.quarterdeck/rules.local.lifecycle.json, mergeGate is tighten-only: a require* flag is on if any layer turns it on, autoMerge is on only if no layer turns it off, and base and aiReviewers may not be set there at all. This one makes the project wait for an AI review too: 

{ "mergeGate": { "requireAiReview": true } }

budget.window is tighten-only there too. A repo layer gets the smaller cap (a null cap never lifts a machine cap), the lower holdAtFraction and the longer hours. The rest of budget merges like any other layer.

Environment

env.json is machine-only: its repo layer is ignored, so a repository can never hand its agents more of your environment. See env.json.

Forges

forges.json is machine-only too, and a repo layer for it is an error. See forges.json.

Services

services.json is machine-only as well, and a repo layer for it is an error. See services.json.

permissions.json

Every permission request an agent makes is answered from these rules, never by trusting all tools. The defaults: 

{
  "default": "ask",
  "rules": [
    { "kind": "read", "decision": "allow" },
    { "kind": "search", "decision": "allow" },
    { "kind": "think", "decision": "allow" }
  ]
}

A rule is { kind, pattern?, decision }. The kinds are read, edit, delete, move, search, execute, think, fetch, switch_mode and other. The decisions are:

  • allow: the agent goes ahead, this once.
  • deny: the request is rejected.
  • ask: you get a card. Your answer is final; a declined card is a rejection the agent sees.

For execute, the pattern matches each command the shell would run, with * and ? as wildcards. For fetch it matches the URL, and for everything else the paths the request touches, as a glob (** crosses folders). The strictest matching rule wins (deny, then ask, then allow), so the order you write rules in does not matter.

An allow only holds inside the repository. A read or command that reaches outside it becomes ask, and no rule can allow a write outside it. If the rules cannot be read, the request is rejected.

Because arrays are replaced whole, a machine layer that adds a rule repeats the defaults it wants to keep. This ~/.quarterdeck/rules.local.permissions.json lets agents run npm test without asking: 

{
  "rules": [
    { "kind": "read", "decision": "allow" },
    { "kind": "search", "decision": "allow" },
    { "kind": "think", "decision": "allow" },
    { "kind": "execute", "pattern": "npm test", "decision": "allow" }
  ]
}

Any shell allow can run arbitrary code

Many programs run other programs when given the right flag, config value or alias (git -c, npm run, make, find -exec), and an interpreter (sh, bash, zsh, node, python, npx and the like) runs whatever it is handed. An execute allow for one of them lets an agent run anything it can be made to run, without a card.

A pattern is matched against the whole of each command, and * matches any run of characters, spaces and dashes included. So a pattern is a prefix match: git * allows git with any arguments, including git -c alias.x='!sh' x, which runs a shell. A command that chains several (&&, ;, | and the like) is split, and every part must be allowed on its own.

Allow the subcommands you mean instead, such as git status * and git diff *. A pattern ending in a space and * needs something after the space, so list the bare command too. Each row below is a machine layer holding only that one execute allow, with the default of ask:

Pattern Command Allowed without a card
git * git status yes
git * git -c alias.x='!sh' x yes
git * git -c core.pager=less push yes
git status * git status --short yes
git status * git status no
git status git status yes
git status * git -c core.pager=less status no
git status * git status && git push no
git diff * git diff --stat yes
npm test npm test -- --watch no
bash * bash -c 'echo anything' yes

The Rules widget and npm run quarterdeck -- doctor warn about every execute allow that is a bare command plus a wildcard (git *, *), names an interpreter or has no pattern, and about a default of allow.

For a safe start, copy rules/examples/hardened.permissions.json to ~/.quarterdeck/rules.local.permissions.json. It allows reads, searches, the bus tools (kind other) and a short list of read-only commands (git status, git diff, git log, git show, git rev-parse, git branch --show-current, ls, pwd), denies git -c and git --config-env, and asks for everything else.

lifecycle.json

Key Default What it sets
autoEndSettleSeconds 120 How long a voyage must stay settled, with nothing open in any project, before it ends itself. The repo layer can lengthen it but never shorten it.
stuckAfterMinutes 30 How long an agent may go without progress before it is stuck.
budget.maxTokensPerTicket 2000000 The token budget for one ticket.
budget.warnAtFraction 0.8 The share of the budget at which you are warned.
budget.window {"hours":5,"capTokens":null,"holdAtFraction":0.8} The rolling token window. Every launch is held once the tokens spent in the last hours reach holdAtFraction of capTokens. capTokens: null means no cap. The Usage widget shows the same window.
mergeGate See the merge gate.

The merge gate

After a builder reports a pull request (a merge request on GitLab), the reviewer reads it and approves it or sends it back. The merge gate then decides whether it merges.

Key Default What it does
requireReviewerApproval true Merge only on the reviewer's approval. Turned off, nobody reads the diff before it merges.
requireChecksPassing true Merge only when the pull request's checks pass. Pending checks wait; failing checks send it back.
requireAiReview false Also wait for an AI review from one of the forge's aiReviewers, and send it back while any thread one of them opened is unresolved. On with no logins listed for the project's forge, the gate stops with an error naming ~/.quarterdeck/rules.local.lifecycle.json instead of passing. The old key requireCopilotReview still works: it reads as requireAiReview, with a deprecation warning, and on GitHub the default logins are Copilot's, so it gates exactly as before.
aiReviewers {"github":["copilot-pull-request-reviewer","Copilot"],"gitlab":[]} The exact bot logins that count as the AI reviewer, per forge. A user account never counts, whatever its login. GitLab has none by default; there the Quarterdeck reviewer agent is the review. Machine-only: the repo layer may not set it.
autoMerge false Squash merge as soon as the gate passes. Off, you get a merge card and nothing merges until you answer it.
base unset The branch pull requests must merge into. Unset, the repository's default branch.

The gate only merges pull requests in the project's own repository, into its base branch.

models.json

One entry per role: planner, driver, builder and reviewer. Each has a runtime and, optionally, a model. Every role uses kiro by default. This ~/.quarterdeck/rules.local.models.json moves the reviewer to Claude Code and leaves the other roles on Kiro: 

{ "reviewer": { "runtime": "claude" } }

naming.json

Agents are named from a list: a theme and its names. The default theme is animals. Names are lowercase letters, digits and hyphens, start with a letter, and must be unique.

env.json

Agents do not inherit the server's environment. They get PATH, HOME, USER, LOGNAME, SHELL, LANG, LC_*, TERM, TMPDIR, TZ, SSH_AUTH_SOCK (so git push over ssh works), Quarterdeck's own QUARTERDECK_BUS_* variables, and the variables their runtime needs to sign in. Anything else, GH_TOKEN, GITHUB_TOKEN and DATABASE_URL included, stays out. Builders open pull requests with gh, which keeps working through its own gh auth login; quarterdeck doctor warns when gh is signed in only through a token variable.

pass lists more names. Values always come from the server's environment; the rule holds names only. The default is empty. Only the machine layer can add names: agents can write to a repository, so a <repo>/.quarterdeck/rules.local.env.json is ignored. This ~/.quarterdeck/rules.local.env.json gives every project's agents AWS_PROFILE: 

{ "pass": ["AWS_PROFILE"] }

Claude auth mode

How Claude Code agents sign in is a setting of the machine, not a rule: it has no repo layer and is never stored in a project's database. Set QUARTERDECK_CLAUDE_AUTH in the environment you start Quarterdeck from, or write ~/.quarterdeck/claude.json; the environment wins when both are set. Quarterdeck reads it each time it starts a Claude agent. 

{ "auth": "api_key" }
Mode What agents get
subscription The default. Nothing is added: Claude Code uses its own stored sign-in.
api_key ANTHROPIC_API_KEY, from the server's environment or, on macOS when it is not set there, from the Keychain item quarterdeck-anthropic-api-key. With neither, the agent does not start and says so.
vertex CLAUDE_CODE_USE_VERTEX=1, plus ANTHROPIC_VERTEX_PROJECT_ID, CLOUD_ML_REGION and, when they are set, GOOGLE_APPLICATION_CREDENTIALS, CLOUDSDK_CONFIG and ANTHROPIC_VERTEX_BASE_URL, passed by name from the server's environment. Credentials come from gcloud's application-default login (gcloud auth application-default login). Without the project id or the region, the agent does not start and says so.

In every mode ANTHROPIC_BASE_URL passes through when it is set, for a gateway. Only these names are added; the rest of the server's environment stays out as described in env.json. The key stays in your environment or the Keychain: Quarterdeck never writes it to the database, an event, a turn file or the notebook, and anything shaped like sk-ant- is replaced with [redacted] before it is stored. To keep the key in the Keychain: 

security add-generic-password -a "$USER" -s quarterdeck-anthropic-api-key -w

The dashboard header shows the active mode, read-only, and quarterdeck doctor reports it with whatever its env is missing.

kiro.json

baseAgents names a Kiro agent of your own for the driver, the reviewer and the builder, so they start with your MCP servers, steering, skills, prompt, tools and model. Every role has none (null) by default. A builder's base is looked up in <repo>/.kiro/agents/ first, then ~/.kiro/agents/; the others only in ~/.kiro/agents/. Quarterdeck always adds its own bus and never copies the base's hooks, and a builder never loads mcp.json. A base from the repo gives only its prompt, resources, tools and model, and may only point at files inside the repo: agents can write there. A repo layer may only set the builder. This ~/.quarterdeck/rules.local.kiro.json starts every builder from ~/.kiro/agents/everyday.json: 

{ "baseAgents": { "builder": "everyday" } }

One project can override that for its own builders, so a component library's builders can start from a different agent than an app's. This <repo>/.quarterdeck/rules.local.kiro.json starts the project's builders from component-builder, looked up in the repository's .kiro/agents/ first: 

{ "baseAgents": { "builder": "component-builder" } }

npm run quarterdeck -- doctor prints the base each role resolves to, or the error naming a missing or broken file.

forges.json

Quarterdeck works out which forge a project is on from the host of its origin remote: github.com is GitHub and gitlab.com is GitLab. A forge on any other host needs a line in forges, mapping its host to github or gitlab. The default is empty. A project whose host is in neither place stops with an error naming the host and this file. This ~/.quarterdeck/rules.local.forges.json puts every project on git.example.org on GitLab: 

{ "forges": { "git.example.org": "gitlab" } }

Only the machine layer can map hosts: a <repo>/.quarterdeck/rules.local.forges.json is an error naming the file. The forge decides the words agents and the dashboard use: pull requests and gh on GitHub, merge requests and glab on GitLab. Doctor checks glab for every host mapped to gitlab here.

services.json

Each project tells its agents which tracker it uses and how to reach it, and every agent prompt carries that in a Services section next to the forge and its CLI. The agents use those tools themselves; Quarterdeck never calls the tracker. projects is keyed by project slug and empty by default. A tracker has a free-text kind and a how: cli with a command, or mcp with a server. Only a kind of none may leave how out. notes is passed on as written. publishes marks a library whose merged tickets must be published before dependents unblock (see work across projects). This ~/.quarterdeck/rules.local.services.json reaches one project's tracker through an MCP server and another's through a CLI: 

{
  "projects": {
    "example": {
      "tracker": {
        "kind": "tracker-mcp",
        "how": "mcp",
        "server": "tracker-mcp",
        "notes": "tickets are stories in the Example board"
      }
    },
    "sample": {
      "tracker": { "kind": "tracker-cli", "how": "cli", "command": "tracker" },
      "publishes": true
    }
  }
}

The dashboard's Project widget sets the same two values for one project and stores them with it; a value set there wins over this file. Only the machine layer can set services: a tracker names a command agents run, so a <repo>/.quarterdeck/rules.local.services.json is an error naming the file.

A ticket's id in the tracker is its external_ref, which the Planner sets when it proposes the ticket; a builder's and the reviewer's Services section name it. Services supersede the ticket-source plugins in ~/.quarterdeck/plugins/.

profile.json and rules profiles

A rules profile is the coding standard agents are told to follow. Every builder's assignment and the reviewer's brief end with the active profile's standards doc and steering block. The shipped default profile is generic and language-neutral: how an agent works a ticket, with no style opinions and no steering block. It is what a new workspace gets.

profile.json names the active profile and any local rule levels: { "profile": "default", "levels": {} }. The machine layer picks one profile for every project; a project's repo layer may pick another, and wins. Levels are 3 (enforced, a disable comment naming the rule is itself a violation), 2 (enforced, a scoped disable comment with a reason is allowed), 1 (warns) and 0 (off). Machine levels apply over the profile's own. A repo layer's levels can only raise a rule's level, never lower it, since agents can write to the repo.

Profiles other than default live on your machine, in ~/.quarterdeck/profiles/<name>/, never in the repository. Each has a profile.json with a description, the standards docs it reads (absolute, or relative to the profile folder), its levels, and optionally a steering source and a setup. A charter.md or reviewer.md there is added to the shipped one, and a lifecycle.json there layers over the shipped lifecycle (a merge gate, say). When a project's repo layer picks the profile, that lifecycle layer can only tighten. Create one with npm run quarterdeck -- profile add <name> --standards <path>, and choose it with npm run quarterdeck -- profile use <name> or the Rules widget, which names the file it writes.

The steering block is generated from the levels, between <!-- quarterdeck-steering:start --> and <!-- quarterdeck-steering:end -->. A profile whose own tool writes the block can name the file and markers in steering; agents then read the block from the repository. A profile's setup names an install command, a levelsFile to write the levels to, and a steer command; init lists what it would run and write and asks first. The default profile has no setup.

charter.md and reviewer.md

The Driver's charter and the reviewer's prompt, in plain Markdown. A rules.local.charter.md or rules.local.reviewer.md replaces the default whole, including what the active profile adds. In a GitLab project, agents read them with every “pull request” and “PR” turned into “merge request” and “MR”.
